# The PER RUN dollar cap does not bound team.spawn workers, so a 5-cent cap ran 24 cents

## Symptom

SETTINGS › SPENDING LIMITS promises PER RUN is a "Hard ceiling for a single agent run. The run stops the moment it would exceed this." With PER RUN at $0.05, one Commander request that delegates to clones spent $0.24 (lead $0.08 + four workers at $0.04 each), plus $0.08 of post-run aux passes. Each spawned worker carries its own full PER RUN ceiling, and the lead itself finished at $0.08, past its $0.05 cap, reason "done".

## Repro

1. Boot with `SKYNET_BUDGET_PER_RUN=0.05` (or set PER RUN to 0.05).
2. Give the lead the orchestrator object and a model that answers its first turn with `team.spawn` of 4 tasks; every model call costs $0.04 (`usage.cost`).
3. Send one message; read every agent.run.end, the ledger and /api/budget/status.

## Evidence

Mechanism: `sidecar/tools/builtin/orchestration.js:926` and `:1189` start each worker/clone with `maxCostUsd: perWorker`, and `perWorker` is `ORCH_PER_WORKER = num(ENV('BUDGET_PER_WORKER'), 0)` (`sidecar/index.js:871`) — 0 means each worker falls back to the full per-run cap (`sidecar/index.js:20382`). Nothing charges worker spend against the lead's run tally. The lead overshoot is the cap being checked between turns. The PER RUN hint is `frontend/app/stationui.js` "Hard ceiling for a single agent run. The run stops the moment it would exceed this."

## Verdict

Fixed: a run and every worker it starts now share ONE per-run cap. `runOnce` gives each run a spend pool at its own per-run cap (`sidecar/run-spend-pool.js`) and puts it on the host-minted tool ctx; `orchestration.js` passes `ctx.spendPool` into every worker, clone, structured-repair and resumed-worker run, which joins it (a request body can never carry one). The run's budget check asks the pool before each paid call: once the family's booked spend reaches the cap — or the calls other members already have in flight would take what is left — that member stops with reason `budget`, scope `run` and the LEAD run's cap, so the COMMS stop line names the cap the Commander set. Each in-flight call is counted at its own member's cost (d42189a18, d42d1bc7e): the member's own largest booked call. A worker with nothing booked yet is counted at the price its loop measured for the call before sending it (prompt tokens at the model's catalog input price), and never below the largest first call a fellow worker has booked. That holds however little is left under the cap (9d4fc52b5). With neither (a pre-call price of $0, as on a model with no catalog price, and no worker data) it counts $0, except when less than one lead turn is left; then the lead's turn is the only evidence there is. A stop on calls still in flight is a projection, not a hit. `loop.js` puts `budgetProjected: true` on agent.run.end (additive, present only when true). COMMS (`chat.js` and `harness.js`), channels (`hub.js`), ACP (`acp/core.js`) and the floor's slag post-mortem (`slaglog.js` via `world.js`) then say the run stopped BEFORE it would pass the cap. Each member's reconciled costs reach the pool as they are booked (a worker starting mid-turn sees the lead's latest call) and its final spend at run end. A run that never delegates is decided by its loop's own check exactly as before (a one-member pool decides nothing). The bound for a family is NOT one call: it passes the cap by at most the call admitted last, plus whatever the calls in flight with it cost beyond what was counted for them. That excess is their output tokens, which nobody can know before the call, and the whole call on a model with no catalog price. The cheap-lead case lands at $0.09 for a $0.05 cap, inside that bound: the second clone was admitted with $0.04 left and the first clone counted at its $0.03 input price. So clones whose input price is far below what their calls bill (output-heavy calls) can start together near the cap and pass it by that uncounted output. The lead-turn floor does not cover that case: it is evidence only for a call with no price. The input price is cache-blind, so a cached prompt is over-counted: the safe side of a spend cap, at the risk of stopping a worker early near the cap. The lead's own between-turn overshoot noted above is the pre-existing single-run bound, unchanged. A flat-subscription lead (no $ cap of its own) bounds the metered crew it starts by PER RUN. Not examined in this fix: the two post-run aux rows the sweep also saw ($0.08 for `agent`) — the regression runs with aux passes off and made no aux call; `BUDGET_PER_WORKER` still lowers a single worker's own ceiling on top of the shared cap. Proven live through the booted sidecar with a mock provider only; no paid-provider run. The follow-ups d42189a18, d42d1bc7e and 9d4fc52b5 were proven through the real loop, orchestration and pool modules. `test/run-cap-bounds-spawn.e2e.test.js` was NOT re-run on any of them, because no sidecar boot was allowed with about 1 GB of RAM free. Its mock model is priced at $0, so the pre-call price is $0 there and its expected result should not change. Fix: `4439b14ee`, `d42189a18`, `d42d1bc7e`, `9d4fc52b5`.
